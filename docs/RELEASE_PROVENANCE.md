# Release provenance contract

Ensō Time releases resolve one immutable source commit before any platform build
starts. The release workflow distinguishes that source commit from the commit and
ref containing the workflow instructions.

## Authorized triggers

| Event | Authorization | Source resolution |
| --- | --- | --- |
| Tag push | A beta tag matching `vMAJOR.MINOR.PATCH-beta.NUMBER` | The tag must peel to the triggering `github.sha` |
| Manual dispatch | Only `v0.1.0-beta.2`, dispatched from `refs/heads/main` | The tag must peel to `fceb6c7929e0cf469de9af482c0fb21da34062d9` |

Manual dispatch is a narrowly scoped backfill mechanism, not a general release
interface. Future releases must use a tag push. A dispatch from another branch,
for another tag, or after the beta.2 tag stops resolving to its approved commit
fails before a build job starts.

The resolver fetches the tag once, records its peeled commit as `source_commit`,
and passes that full SHA to every job. The resolver, each matrix build, and the
publisher check out that SHA and verify `HEAD`. Immediately before publication,
the publisher fetches the tag again and refuses to publish unless it still peels
to the same source commit.

The workflow cannot make the final tag check and the GitHub release API call one
atomic operation. Repository rules must therefore prevent tag deletion or movement;
without that external control, a privileged actor could race the short interval
between the check and publication.

Only the publisher job enters the protected GitHub environment named `release`.
That environment must exist before any release is triggered and must require an
authorized reviewer. The matrix build jobs deliberately remain outside it and
retain read-only repository permissions. A repository ruleset must also restrict
creation, update, and deletion of release tags matching `v*`; the environment does
not prevent GitHub from running a historical workflow attached to an unprotected
tag.

## Signed attestations

Each of the four installers is a subject of two GitHub/Sigstore attestations:

1. The standard SLSA provenance generated by `actions/attest` in the publisher
   job. Its certificate identifies the repository, workflow invocation, workflow
   ref, and workflow commit supplied by GitHub Actions. It does not independently
   identify each matrix build job that uploaded an installer.
2. A custom predicate of type
   `https://github.com/mateofh/enso-time/attestations/release/v1`. It records the
   release tag, immutable source commit, workflow commit/ref, invocation metadata,
   and the SHA-256 name/digest pair for every installer.

The custom predicate is necessary for the beta.2 backfill because GitHub correctly
identifies the hardened workflow on `main` as the signer, while the separately
checked-out source is the older immutable tag. The custom predicate makes that
separation explicit rather than describing the workflow commit as the application
source commit.

The release attaches:

- `SHA256SUMS`;
- the standard Sigstore bundle;
- the custom release-binding Sigstore bundle; and
- the readable JSON used as the custom predicate.

### Fail-closed verification

Choose the expected commits from reviewed repository state, not from fields inside
the downloaded attestation:

- Future tag push: `WORKFLOW_COMMIT=SOURCE_COMMIT=OIDC_SOURCE_COMMIT=<peeled tag commit>`.
- Beta.2 backfill: `OIDC_SOURCE_COMMIT=WORKFLOW_COMMIT=<audited main commit>` and
  `SOURCE_COMMIT=fceb6c7929e0cf469de9af482c0fb21da34062d9`.

For a tag push, GitHub's signer and source certificate extensions both identify
the tagged commit, which also contains the workflow. For the manual backfill, the
OIDC token is issued for the audited workflow invocation on `main`, so its signer
and source extensions both identify `WORKFLOW_COMMIT`. Checking out beta.2 cannot
and must not rewrite those certificate fields; the separately checked-out
`SOURCE_COMMIT` is instead bound by the signed custom predicate.

Set the expected values and verify the standard provenance:

```bash
INSTALLER="./enso-time-0.2.0-beta.1-macos-arm64.dmg"
RELEASE_TAG="v0.2.0-beta.1"
WORKFLOW_COMMIT="REPLACE_WITH_AUDITED_40_HEX_WORKFLOW_SHA"
SOURCE_COMMIT="REPLACE_WITH_AUDITED_40_HEX_SOURCE_SHA"
OIDC_SOURCE_COMMIT="REPLACE_WITH_AUDITED_40_HEX_OIDC_SOURCE_SHA"
PREDICATE_TYPE=https://github.com/mateofh/enso-time/attestations/release/v1

test -f "$INSTALLER"
test -f SHA256SUMS
[[ "$RELEASE_TAG" =~ ^v[0-9]+\.[0-9]+\.[0-9]+-beta\.[0-9]+$ ]]
for commit in "$WORKFLOW_COMMIT" "$SOURCE_COMMIT" "$OIDC_SOURCE_COMMIT"; do
  [[ "$commit" =~ ^[0-9a-f]{40}$ ]]
done

gh attestation verify "$INSTALLER" \
  --repo mateofh/enso-time \
  --signer-workflow mateofh/enso-time/.github/workflows/release.yml \
  --signer-digest "$WORKFLOW_COMMIT" \
  --source-digest "$OIDC_SOURCE_COMMIT"
```

Verify the custom predicate under the same certificate policy and save only the
already-verified result for structural checks:

```bash
gh attestation verify "$INSTALLER" \
  --repo mateofh/enso-time \
  --signer-workflow mateofh/enso-time/.github/workflows/release.yml \
  --signer-digest "$WORKFLOW_COMMIT" \
  --source-digest "$OIDC_SOURCE_COMMIT" \
  --predicate-type "$PREDICATE_TYPE" \
  --format json > VERIFIED_RELEASE_ATTESTATION.json
```

`gh attestation verify` checks the downloaded installer's digest against the signed
subject. Independently confirm that the attached checksum manifest, signed subject,
and custom predicate all name the same bytes and that the predicate records the
reviewed source/workflow commits:

```bash
ASSET_NAME="$(basename "$INSTALLER")"
ASSET_SHA256="$(shasum -a 256 "$INSTALLER" | awk '{print $1}')"
grep -Fqx "$ASSET_SHA256  $ASSET_NAME" SHA256SUMS

jq -e \
  --arg name "$ASSET_NAME" \
  --arg sha256 "$ASSET_SHA256" \
  --arg releaseTag "$RELEASE_TAG" \
  --arg sourceCommit "$SOURCE_COMMIT" \
  --arg workflowCommit "$WORKFLOW_COMMIT" \
  'length >= 1 and all(.[].verificationResult.statement;
    any(.subject[]; .name == $name and .digest.sha256 == $sha256)
    and .predicate.releaseTag == $releaseTag
    and .predicate.sourceCommit == $sourceCommit
    and .predicate.workflow.commit == $workflowCommit
    and any(.predicate.assets[]; .name == $name and .sha256 == $sha256)
  )' VERIFIED_RELEASE_ATTESTATION.json
```

For beta.2, set `RELEASE_TAG=v0.1.0-beta.2`. Do not substitute the historical
beta.2 commit into `--source-digest`: that flag verifies the GitHub OIDC source
extension, which is the audited `main` workflow commit for a manual dispatch.

## Security limits

An attestation proves the artifact digest and the identity of the workflow that
signed a statement. Fields inside a custom predicate are assertions made by that
workflow; they are not independently guaranteed by Sigstore. The value of this
binding therefore depends on reviewing the pinned workflow and its fail-closed tag
checks. GitHub's CLI documentation makes the same distinction between certificate
identity and user-controllable predicate contents.

Provenance does not prove that the application is secure. It also does not replace
Apple notarization, Windows Authenticode, or the paid signing identities that this
public beta does not use.

The Windows build uses the `windows-2022` hosted image. Before invoking WiX, it
executes a temporary `.vbs` file with `cscript.exe`; merely finding the executable
is not sufficient. The workflow does not enable optional operating-system features
or request a runner restart.

For Windows packaging only, the generated `ci-bundle.json` overrides Tauri's
`productName` to the printable-ASCII value `Enso Time`. WiX 3 links the en-US MSI
through Windows Installer's code-page-bound string pool, and the brand's `ō`
(U+014D) is not safely representable there. The committed Tauri configuration,
macOS bundle name, and explicit application window title remain `Ensō Time`; the
override only supplies the Windows MSI/NSIS packaging identity. Both installer
formats remain required and are smoke-tested after bundling.
